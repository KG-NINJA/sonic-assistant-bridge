# 永続状態と非公開 Site への組み込み

[English](durable-state.md) · [自分で構築する](build-your-own.ja.md)

D1 アダプターと複数 Worker の配送制御を実装し、SQLite を使った模擬 D1 バインディングで試験しました。実 D1 の接続・移行、実行時の暗号鍵、Worker 配備、dot の受信は未検証です。`createSitesReceiver` は外部配送処理を組み込まず、購読作成と送信を無効に保ちます。

## 保存する内容と停止の意味

`bridge/d1-store.js` は、サーバーが渡す抽出不可の AES-GCM-256 鍵で所有者ごとの状態を暗号化します。サーバーで確定した Site と利用者の組を SHA-256 の索引にし、購読、callback と署名秘密、期限、重複・連発制限、解除世代、進行中配送を保存します。暗号化は所有者の索引、スキーマ、更新番号、鍵ラベルにも結び付けます。DB 管理者には索引・更新番号・暗号文サイズ・更新時刻が見えます。保存内容や活動ログを公開成果物へ含めないでください。

読み込みごとに `withSession('first-primary')` を開始し、前回の更新番号と一致する場合だけ SQL を更新します。確定した競合のみ再試行し、その中の処理には通信などの副作用を入れません。書き込みエラーは結果不明として扱い、状態を照合するまで再送や後続通信を行いません。スキーマ欠落、改変、鍵の不一致は拒否し、状態を初期化して通過させません。読み取りだけなら行を書き直しません。[D1 Sessions の仕様](https://developers.cloudflare.com/d1/worker-api/d1-database/#withsession)

所有者ごとに一件の永続配送予約を持ち、challenge とイベントに共通で使います。購読解除は世代を進め、購読を除去し、予約を解除対象にします。別 Worker は解除後の新規配送を予約できません。進行中の Worker は最新状態を確認し、Node 配送処理も DNS 検証後・接続直前に再確認します。開始済みの HTTP 要求や受理済み callback を取り消す保証ではありません。

| 状態 | 意味 |
| --- | --- |
| `not-stopped` | 購読が有効。進行中の一件があれば追加送信は待機します。 |
| `pending`、配送一件 | 購読は無効ですが開始済み処理の終了が未確認。HTTP 解除 API は 202 を返します。 |
| `confirmed`、配送ゼロ | 購読が無効で未終了の予約もありません。HTTP 解除 API は 200 を返します。既に受理された callback は取り消せません。 |

MCP `events/unsubscribe` は購読を解除します。配送の終了は `sonic_bridge_status` または画面の再確認で確かめます。解除後に届いた 2xx を配送成功とせず、古い 410 が新しい購読を解除しないようにしています。期限切れや時計の飛びだけでは予約を解放しません。停止していた Worker が再開する可能性があるためです。Worker の消失や書き込み結果不明では、管理者が終了を裏付けられるまで停止確認待ちが残ります。自動解除やブラウザーからの強制リセットはありません。

購読は最大一時間、重複 ID は鮮度判定の期間内で最大 512 件、動きの配送は三秒に一件・一分に 60 件までです。期限切れ情報は後続の操作で整理します。定期削除処理はないため、操作されない所有者の暗号化行は残り得ます。バックアップはホストの保持方針に従います。購読解除はデータ削除ではありません。利用前に保持期間を定めて説明してください。暗号鍵やラベルの変更には計画的な移行が必要です。

## 自分の非公開 Site へ組み込む

1. 再開時は登録済みの同じ Site を使い、所有者限定の公開範囲とソース識別情報を保ちます。インストール済み Sites の `project-setup.mjs` / `site-workflow.mjs` と、標準入力で認証情報を渡す正規手順を使います。ヘルパーがない環境で認証処理を作り直したり Site を重複登録したりしません。
2. 公式のサーバースターターを使い、`migrations/0001_bridge_state.sql` の定義を `db/schema.ts` と移行手順へ反映し、`npm run db:generate` を実行します。生成 SQL・snapshot・journal をまとめて確認します。同梱 SQL は試験したスキーマであり、Sites/Drizzle の完成済み配備パッケージではありません。生成器が表せない定義は対応する正式な custom migration を使います。適用済み移行は書き換えず、追加分を作ります。リクエスト処理でテーブルを作成しません。
3. スターターの正式な形式で論理 D1 バインディングを `.openai/hosting.json` に宣言します。実 DB ID は推測せず Sites に任せます。canonical plugin 用の `capabilities: ["mcp"]` を維持します。ローカル移行と本番移行は別です。公開手順では Worker のアップロード前に移行します。結果不明なら読み戻してから再試行します。
4. 永続的な AES-GCM-256 鍵を正式なサーバー実行時秘密の経路で渡し、encrypt/decrypt 用・抽出不可で読み込みます。安定した鍵ラベルとともに `createSitesReceiver` へ渡します。このリポジトリは鍵を生成しません。要求ごとの再生成、ID からの派生、ログ出力、ソース・HTML・ブラウザーへの埋め込みは禁止です。
5. サーバーバンドルに `bridge/sites-receiver.js`、`d1-store.js`、`private-handler.js`、`service.js`、`mcp-events.js`、参照先の `src/bridge.js` を含めます。返されたハンドラーを **Sites Dispatch の後段だけで** `/mcp` と `/api/bridge/*` に接続します。身元ヘッダーを一般公開サーバーで信頼しません。同じ認証済みオリジンで既存の英日測定画面を配信し、そこでだけ非公開画面のマーカーを付けます。マイク・送信の明示開始と非表示時停止を維持します。
6. 公式のビルド・ソースヘルパーで検査、commit、梱包、保存、同じ Site への公開を進めます。公開用 `pages/` と持ち運び用 `dist/` はプレビュー／ローカル模擬実行用で、非公開サーバーの成果物ではありません。共有用ソースには `node_modules`、ログ、実行時の秘密、私的 ID、実行データを含めません。

現在の Site 用構成は、設定後に認証済み状態確認・発見・解除と永続保存を使える設計です。配送は有効にできません。D1 と Worker 配送の確認は別問題です。`global_fetch_strictly_public` は同一 zone への公開経路を文書化していますが、Sites の実ビルド・ホストへの反映と、接続時の宛先保護は未確認です。フラグやホスト名許可だけで有効化しません。Workers では `redirect: 'manual'` と全 3xx 拒否を使い、`redirect: 'error'` は使えません。この変更だけで宛先保護が解決するわけでもありません。[互換性フラグ](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#global-fetch-strictly-public)、[Workers Request](https://developers.cloudflare.com/workers/runtime-apis/request/)

## 費用と試験の範囲

D1 の読み書き・保存、ホストの要求、外部通信は契約により費用が生じます。解除確認は配送要求の実行中だけ、既定 50 ms・同時一読込で行いますが、読込量は増えます。バックグラウンドの再送キューはありません。無料と仮定せず、利用前に上限と停止方法を決めてください。この試験で有料契約や支出上限は変更していません。

Node 22.13 以降（SQLite 試験 API）または Node 24 で `node --test test/d1-store.test.js test/d1-service.test.js test/dispatch.test.js` を実行します。暗号化、競合、再起動、書込結果不明、改変、解除競合、遅延応答を検証します。実 SQLite と模擬 D1 API の試験であり、実 D1 の遅延・複製、Worker の寿命、実行時秘密の利用可否、物理的な通信中止の証拠ではありません。実接続では別途検証し、対応するイベントが会話に届いたことまで確認します。
