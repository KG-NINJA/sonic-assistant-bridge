# Durable state and private Site packaging

[日本語](durable-state.ja.md) · [Build your own](build-your-own.md)

The D1 adapter and shared dispatch controls are implemented and tested with SQLite behind a simulated D1 binding. No live D1 binding, hosted migration, runtime encryption key, Worker deployment, or dot receipt has been verified. `createSitesReceiver` deliberately installs **no outgoing transport**; subscription creation and event delivery stay blocked.

## State and stop semantics

`bridge/d1-store.js` encrypts each owner's bounded state with a server-supplied, nonextractable AES-GCM-256 key. The index is SHA-256 of the server-derived Site/user pair; the encrypted payload contains the subscription, callback/signing material, expiry, rate/dedup state, revocation epoch, and outstanding dispatch. Encryption authenticates the owner index, schema version, revision, and key label. Database administrators can still see the hashed index, revisions, ciphertext size, and update times. Do not put these records or activity logs into public artifacts.

Each read starts a new `withSession('first-primary')` session; changes use conditional SQL with the previous revision. Only a confirmed revision conflict retries a pure synchronous mutator. A thrown write has an unknown result: no resend or downstream network effect is allowed before reconciliation. Missing schema, invalid ciphertext, wrong key, and exhausted retries fail closed. Unchanged reads do not rewrite the owner row. See the [D1 Sessions contract](https://developers.cloudflare.com/d1/worker-api/d1-database/#withsession).

One durable permit per owner covers callback verification and event delivery. Unsubscribe advances the epoch, removes the subscription, and marks any permit revoked. A different worker therefore cannot admit new delivery after revocation. An in-flight worker polls fresh state, and the Node transport checks permission again after DNS validation immediately before opening the connection. These controls cannot recall an HTTP request that was already admitted or accepted.

| Status | Meaning |
| --- | --- |
| `not-stopped` | Subscription is active; a pending dispatch can still temporarily prevent sending. |
| `pending`, one dispatch | Subscription is inactive, but admitted work has not been confirmed settled. HTTP unsubscribe returns 202. |
| `confirmed`, zero dispatches | Subscription is inactive and no outstanding permit remains. HTTP unsubscribe returns 200. Previously accepted callbacks cannot be recalled. |

MCP `events/unsubscribe` removes the subscription; use `sonic_bridge_status` or the private status API to check dispatch settlement. A late callback 2xx after revocation is not acknowledged as delivery. A stale 410 cannot revoke a newer subscription. Timeouts and clock jumps never recycle a permit: an old worker may resume. If a worker dies or a write result is lost, the permit remains blocked until an operator can prove the operation settled; there is no automatic unlock or browser reset endpoint. Do not clear it merely because a deadline passed.

Subscriptions expire within one hour. Deduplication holds at most 512 IDs for the freshness window; delivery is limited to one motion per three seconds and 60 per minute. Expired records are pruned on later owner operations, not by a scheduled deletion service. An inactive owner's encrypted row can persist; backups follow the host's retention policy. Unsubscribe is not account/data deletion. Configure and disclose a retention policy before use. A changed encryption key/label requires a controlled migration; changing settings alone must not reset state.

## Package into your own private Site

1. Reuse the exact already registered Site when continuing a deployment. Preserve its owner-private audience, source identity, and logical binding names. Use the installed Sites `project-setup.mjs` / `site-workflow.mjs` helpers and their documented credential-on-stdin flow. Do not reconstruct helper authentication or create a duplicate Site when the helpers are absent.
2. Use the maintained server starter. Bring the definitions in `migrations/0001_bridge_state.sql` into its `db/schema.ts`/migration workflow, run `npm run db:generate`, and inspect the generated SQL, snapshots, and journal together. The supplied SQL is the tested schema contract, **not a complete Sites/Drizzle deployment package**. Use a supported custom migration for any definition the generator cannot express. Keep applied migrations immutable and append later changes. Never run schema creation in request handlers.
3. Declare the logical D1 binding using the starter's supported `.openai/hosting.json` shape; Sites provisions the actual binding. Do not guess database IDs. Keep `capabilities: ["mcp"]` for the canonical private plugin. Apply preview migrations locally; hosted migrations are applied through the Sites publication workflow before the Worker upload. Read back uncertain migration/deployment outcomes before retrying.
4. Supply a persistent AES-GCM-256 key through the documented server runtime secret mechanism, import it as nonextractable with encrypt/decrypt usage, and pass it with a stable key label to `createSitesReceiver`. No key is generated by this repository. Do not regenerate it on each request, derive it from an ID, log it, or put it in source, HTML, build assets, or a browser token.
5. Include `bridge/sites-receiver.js`, `d1-store.js`, `private-handler.js`, `service.js`, `mcp-events.js`, and their local import `src/bridge.js` in the server bundle. Mount the returned handler at `/mcp` and `/api/bridge/*` **only behind Sites Dispatch**. The trusted identity header is unsafe on a directly reachable unauthenticated origin. Serve the existing EN/JA capture assets on that same authenticated origin, adding the private UI marker only there. Keep microphone/sending opt-in and hidden/pagehide stop.
6. Use the official build/source helper to verify, commit, package, save, and publish the same Site. The public `pages/` and portable `dist/` outputs are previews/local mock runtimes; neither is the private server artifact. Do not include `node_modules`, logs, runtime secrets, private IDs, or runtime data in shareable source packages.

The current Site assembly offers authenticated status/discovery/revocation and durable storage once configured. It intentionally cannot enable delivery. Its lack of a Worker sender is separate from D1 readiness. `global_fetch_strictly_public` documents public routing for a Worker's own zone; propagation through the actual Sites build/hosting pipeline and the required connection-time address protections remain unverified. A flag or hostname allowlist alone does not enable delivery. Workers supports `redirect: 'manual'` with explicit rejection of all 3xx, not `redirect: 'error'`; this detail alone does not resolve address safety. [Compatibility flags](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#global-fetch-strictly-public), [Workers Request](https://developers.cloudflare.com/workers/runtime-apis/request/).

## Costs and remaining verification

D1 reads, writes, storage, hosting requests, and outbound requests may incur costs under your provider's plan. Revocation polling runs only while an outgoing request is active (default 50 ms, at most one read in flight), but still adds reads. There is no background retry queue. Do not assume free operation; choose limits and stop controls before enabling your own connection. No paid contract or budget limit was changed during these tests.

Use `node --test test/d1-store.test.js test/d1-service.test.js test/dispatch.test.js` with Node 22.13+ (SQLite test API) or Node 24. Tests cover encrypted persistence, concurrent revisions, restart, uncertain writes, tampering, stop races, and late responses. They simulate the D1 API using real local SQLite; they do not establish hosted D1 latency, replication, Worker lifecycle, runtime-secret availability, or physical network cancellation. Those require separate private deployment tests. Actual conversation receipt still requires matching event evidence after a supported subscription and safe transport are available.
